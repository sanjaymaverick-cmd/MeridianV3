## Verdict

**Do not train on the shipped artifacts. Do not arm live yet.** Paper trading itself is safe to keep running — the live-arm chain is genuinely gated (disarmed by default, unattended autopilot hardcodes `live_armed=False`, and no order reaches a real venue without a broker adapter that isn't in this repo). But the book's own honesty is currently broken in two independent, additive ways: (1) prices are Yahoo **daily closes** refreshed every few minutes, so a large fraction of same-day paper clips open and close at the identical mark and are booked as directional losses that are really just brokerage/GST; (2) a still-reachable unit-mismatch bug prices India-futures entries at roughly **1/3.077** of the real mark whenever a derived symbol's price cache is momentarily empty, fabricating a ~100% win rate on those clips. Both effects are visible, quantified, and reproduced below directly against the live DB. The single global Beta(α,β) belief that both the live decision engine and any future retrain would lean on (`alpha=66, beta=158`, mean 29.5%) is a mixture of these two artifacts, not a measurement of edge. Separately, the "meta-label logistic" and the "V1 five-factor score" that the docs describe as learning components are both dead code in production — one never receives an `update()` call, the other's table has zero rows — so the system is simpler, and less adaptive, than it presents itself as.

## Findings

### F1 — Severity: critical — Daily-close marks under an intraday auto-loop fabricate same-price "losses" that poison the belief model

- **File:** `meridian_v3/data_providers/service.py:49` (`_history`, `yf.Ticker(ticker).history(period="6mo", ...)` — yfinance default interval is daily), `meridian_v3/autopilot.py:198` (`persist_belief(session, won=float(out.get("pnl") or 0) > 0)`), `meridian_v3/config/default.yaml:alerts.poll_seconds: 60`.
- **What I verified:** Queried the live book directly. Of 190 closed paper positions with a recorded `exit_price`, **123 (65%)** have `avg_price == exit_price` to the cent. All 123 are booked as losses (`realized_pnl` uniformly negative, e.g. −₹6.37, −₹6.27, −₹6.58 — exactly the brokerage+GST bill). Fill notes confirm the exit reason is uniformly `"End of day — flattening the same-day paper clip."`, i.e. the tape simply never moved between the buy and the EOD flatten, because `price_cache.last` is a daily Yahoo close that `PriceProvider.refresh()` only re-fetches on a ~5-tick (≈5 min) cadence and the underlying daily bar itself only updates once a trading day. `autopilot.persist_belief` then records every one of these as a loss (`won = pnl > 0`, and `pnl = -fees < 0` when price is unchanged).
- **Why it matters:** This is the load-bearing bug of the whole "learning loop." The single global `beliefs` row (`rule_name='core'`) sits at `alpha=66, beta=158` (mean 29.5%) in the live DB — a number that will suppress Kelly sizing and the live-confidence gate — but it is dominated by fee-only non-events, not genuine directional misses. Any retrain or live-arm decision based on this belief, or on `y_binary`/`honest_pnl` in the training CSV, is training on "the broker's bill," not on the model's skill.
- **What "fixed" would look like:** Either (a) pull intraday quotes (Yahoo `interval="1m"`/`"5m"` intraday history, or a streaming source) so a same-day clip can actually move, or (b) if intraday data isn't available, stop treating a zero-move EOD flatten as a training-worthy trade outcome at all — exclude `exit_reason == EOD flatten AND price unchanged` from `persist_belief`/`build_meta_labels.py`, and label it "no signal, cost only" rather than a win/loss.

### F2 — Severity: critical — India-futures fill price still reachable at ~1/3.077 of the real mark when a derived symbol's cache is momentarily empty

- **File:** `meridian_v3/execution/oms.py:249-260` (`_fill_price`), `meridian_v3/pipeline.py:257` (`last = cache.last if cache and cache.last else 0.0`), `meridian_v3/capital/sizer.py:168-195` (`india_futures` branch — `notional` = margin, `qty` = lots).
- **What I verified:** Live DB: 43 closed `INFY.F` and 8 closed `NIFTY.F` positions carry `exit_price / avg_price ≈ 3.077` exactly (e.g. id 52: avg `380.185`, exit `1169.80`; id 40's fill: buy `7,924.05`, sell `24,381.70`). `3.077 = 1 / (contract_size(65) × lot_step(0.05) × margin_pct(0.10))` — i.e. `decision.price` was falsy (0/None) at entry time, so `_fill_price()` fell back to `decision.size.notional / decision.size.qty`, and for `india_futures` that notional field is **margin**, not price (the same class of bug the branch's own commit message references, but not fully closed). The fix at `oms.py:256` only helps when `decision.price` is already valid; it does nothing when the upstream cache lookup returns 0. Fresh rebuild of the training set (`python build_meta_labels.py`, run against the live DB) shows `INFY.F: 43 wins / 43 trades, avg pnl +₹37.86` — a fabricated 100% win rate.
- **Why it matters:** This single symbol class contributes 43 of the 56 "wins" in the current book and skews `beliefs.alpha` upward by the same amount the EOD-flatten bug skews `beta` upward — the two bugs partially cancel in the belief mean but both are noise, not signal, and the training CSV inherits both.
- **What "fixed" would look like:** `_fill_price()` should never divide margin by lots. If `decision.price` is unavailable, the order should be rejected/held (as it already is for `price<=0` in `size_position`), not silently priced from `notional/qty`. Also worth asserting a sanity bound (e.g. reject a fill whose price is off from `price_cache.last` by more than some %) as a second line of defense.
- **Scope note:** the same `notional = margin` mechanism applies to every `global_commodities` symbol (`_crypto_size()` is shared by `crypto_spot`, `crypto_futures`, and `global_commodities`), not just SILVER.X/GOLD.X — CORN.X and WHEAT.X are equally exposed to the same 10× (`1/margin_pct`) slide whenever their price cache is momentarily empty at decision time; this snapshot's closed positions happened not to include either symbol, but the code path is identical.

### F3 — Severity: critical — `repair_shifted_clips` overwrites historical entry price with today's live mark, and can never repair rows missing `exit_price`

- **File:** `meridian_v3/storage/repair.py:43-76` (`repair_shifted_clips`), specifically line 57 (`pos.avg_price = new_avg` — unconditional) vs. lines 55/59 (`exit_price`/`realized_pnl` updates gated behind `if pos.status == "closed" and pos.exit_price:`).
- **What I verified:** Reproduced directly against a copy of the live DB (not the original file). Position id 12 (`INFY.F`) before repair: `avg_price=380.055, exit_price=None, realized_pnl=None`. `_mark_for()` returns `price_cache.last` (1169.20, today's spot) because `exit_price` is null. `align_prices(380.055, 1169.20, 'india_futures')` finds scale `3.077` (via the market-specific fallback branch, not just the generic 10×/100× table) and rewrites `avg_price → 1169.40`. Running `repair_shifted_clips` leaves `exit_price` and `realized_pnl` at `None` — permanently, because those two fields are only touched inside an `if pos.exit_price:` block that is false by construction for these rows. 26 of 216 closed positions in the live DB (12%) are in this state.
- **Why it matters:** This is worse than a no-op. Every time `repair_shifted_clips` runs — which is on every process boot (`storage/db.py:_repair_book`) and on every `/book` page load (`ui/routes.py:137`) — it silently replaces the one honest number these rows still had (the original, if mispriced, fill price) with whatever the current live tape happens to be, chasing a moving target. The position can never be reconciled to a real P&L; `exit_price`/`realized_pnl` stay `NULL` forever. `build_meta_labels.py` sidesteps this specific symptom (it reconstructs from `fills`, not `positions`), but the underlying `Fill.price` for these entries is still the original buggy 380.06 — repair only touches the `Position` row here, not the `Fill` row, because `_scale_fills` also requires the fill to "look shifted" against a `mark` that in this branch is already the (now-wrong-again) live price, not the original exit.
- **What "fixed" would look like:** Repair should refuse to touch `avg_price` for a closed position that has no `exit_price` (there is nothing to align it to), and should instead flag those rows for manual reconciliation or reconstruct them once from the matching `Fill` pair (which does exist and does carry the real numbers, per Finding F2's fill-note evidence).

### F4 — Severity: high — Meta-label logistic never learns in production; "p_success" is a fixed formula, not a trained model

- **File:** `meridian_v3/engine/meta_label.py:92-121` (`OnlineLogit`), `meridian_v3/decision/engine.py:57,105` (`DecisionInput.logit: OnlineLogit | None = None`, `meta = meta_label(inp.primary, features, inp.logit, min_p=0.52)`), `meridian_v3/pipeline.py` (never sets `logit=`).
- **What I verified:** `grep -rn "OnlineLogit" meridian_v3/` shows the class is only ever referenced in its own definition, in `decision/engine.py`'s type-hinted-but-unset field, and in `tests/test_meta_label.py::test_online_logit_learns` (which tests the class in isolation, calling `.update()` directly — it does not exercise the pipeline). Since `inp.logit` is always `None`, `meta_label()`'s `mdl = model or OnlineLogit()` builds a brand-new, zero-`updates` instance on every call, so `predict()` always takes the `if not self.trained` branch → `_cold_start_p(features)`, a fixed linear formula over confluence/primary/freshness/cost. Live `signals` table (23,651 rows) confirms: `p_success` takes essentially two distinct values across the whole book.
- **Why it matters:** README, docs/02-auto-decision.md, and docs/05-mathematics.md §4 all describe this as "updated from paper wins and losses," which is the entire premise of the meta-labeling architecture (López de Prado pattern, per the module docstring). It is not happening. The live-gate ("confidence ≥ 0.82") and the training feature `p_success` are both, today, a static heuristic rather than a model that improves with paper history.
- **What "fixed" would look like:** Persist logistic weights per rule (a new table, or piggyback on `beliefs`), load them into `DecisionInput.logit` in `pipeline.py`, and call `.update()` from the same place `persist_belief` is called in `autopilot.manage_exits`/`flatten_india_paper`.

### F5 — Severity: high — V1 five-factor score is entirely dead code

- **File:** `meridian_v3/scoring/composite.py` (never imported anywhere under `meridian_v3/`), `meridian_v3/pipeline.py:134-137` (`FactorScore` query, `score = score_row.composite if score_row else 6.5`).
- **What I verified:** `grep -rln "from meridian_v3.scoring"` across the whole package returns no hits. `grep -rn "FactorScore("` shows the class is only ever constructed in its own definition (`storage/schema.py`) — nothing inserts a row. `select(count(*)).from(factor_scores)` on the live DB returns `0`. So `score_row` is always `None` and `pipeline.py` always uses the literal constant `6.5` for every symbol, every cycle.
- **Why it matters:** ARCHITECTURE.md's layer diagram and folder map present V1 ("five-factor score · hysteresis... factors / regime / tape") as a live input to V2/V3. It is not connected to the auto-decision cycle at all; the "score" vote in `confluence` (`FactorVote("score", ((score or 5) - 5) / 5, 0.8, ...)`) is a constant `0.3` for literally every name on the desk.
- **What "fixed" would look like:** Either wire a `FactorScore`-writing step into the cycle (or the price refresh), or remove the dead read path and stop presenting V1 scoring as part of the live pipeline in the architecture doc.

### F6 — Severity: high — Router's competing-market scores are unreachable; routing is pure suffix dispatch

- **File:** `meridian_v3/router/markets.py:76-107` (`route_market`), `meridian_v3/pipeline.py:198-204` (hardcoded `equity_score`/`commodity_score`/etc. and `preferred_market=market_for(...)`).
- **What I verified:** `route_market()`'s first statement is `if preferred: return Route(preferred, 100.0, ...)` — an immediate return before the equity/options/futures/commodity/crypto/forex score comparison that follows it ever executes. `pipeline.py` always computes and passes `preferred_market=market_for(item.asset_class, item.symbol)`, and `market_for()` (in the same file) always returns a market string (falls back to `CLASS_TO_MARKET.get(asset_class, "equity_cash")` — never `None`). So the `equity_score=70/40`, `commodity_score=74/15`, etc. constants computed in `pipeline.py:198-203` (exactly the "hardcoded score of 74" pattern this audit was asked to check for) are passed into a function that never reads them in the live cycle.
- **Why it matters:** ARCHITECTURE.md and docs/02/docs/06 describe a tape-competition router ("Equity cash is home... Shift is allowed because this tape beats home by N points"). That code path exists, is unit-tested in isolation, and is simply never invoked from the real cycle — every symbol is hard-assigned to a market by its suffix (`.X`, `.F`, `.C`, `USDT`, FX-pair membership) with no runtime competition. This isn't itself dangerous (suffix dispatch is arguably safer than a score fight), but it is not what the docs claim is happening, and the dead scores are exactly the kind of hardcoded constant this audit was primed to flag as a risk if it *did* steer the book — worth confirming it doesn't, in writing.
- **What "fixed" would look like:** Either drop `preferred_market` from `pipeline.py` and let the scores genuinely compete, or delete the score-comparison branch of `route_market()` and document routing as suffix-based, matching reality.

### F7 — Severity: high — `build_meta_labels.py` round-trip pairing drops shorts and can mispair a cover-buy with an unrelated open-sell

- **File:** `build_meta_labels.py:231-262` (`reconstruct_honest_roundtrips`).
- **What I verified:** The pairing loop only advances by 2 (and records a trade) when `grp.loc[i]["side"]=="buy" and grp.loc[i+1]["side"]=="sell"`; any other adjacent pattern advances by 1 without pairing. Traced by hand: for the sequence `[sell(open short), buy(cover), buy(open long), sell(close)]` the algorithm correctly skips the short and pairs only the long — but for `[sell(open short₁), buy(cover₁), sell(open short₂), buy(cover₂)]` it would pair `buy(cover₁)` with `sell(open short₂)` as a fabricated "long" round-trip, because the algorithm has no notion of position state, only adjacency. In the live DB this did not fire: `select side, count(*) from positions` shows **217/217 positions are `side='buy'`** — no shorts were actually opened in this snapshot, so the bug is latent, not yet triggered. It is a live code path, though: `decision/engine.py:132-137` explicitly allows `sell`-to-open on `india_futures`, `crypto_futures`, `forex_micro`, and `global_commodities`.
- **Why it matters:** The moment this book (or a future session) opens even one short, this builder will silently either drop it or manufacture a fictitious long trade from unrelated fills, without any error or row-count anomaly to signal it happened.
- **What "fixed" would look like:** Track running position/side state per symbol while walking fills (a small stack per symbol, push on open, pop on matching-side close) instead of naive adjacent-pair matching.

### F8 — Severity: high — Shipped training artifacts are stale and mutually inconsistent; do not reflect the live book

- **File:** `meridian_v3_meta_labels.csv`, `artifacts/meridian_v3_meta_labels.csv`, `README_MeridianV3_MetaLabels.md`, vs. `meridian_v3.db` / `meridian_v3_with_meta_labels.db` / `artifacts/meridian_v3_with_meta_labels.db`.
- **What I verified:** The checked-in CSVs (55 rows each) contain trades on `HDFCBANK` and `TCS` at specific fill prices (e.g. HDFCBANK buy `1671.97` → sell `727.00`, `honest_pnl -₹4,730.69`). A direct query of **every** `.db` file present in the folder (`meridian_v3.db`, `meridian_v3_with_meta_labels.db`, `artifacts/meridian_v3_with_meta_labels.db`) for `symbol='HDFCBANK'` or `'TCS'` fills returns **zero rows** in all three. `README_MeridianV3_MetaLabels.md` describes yet a third snapshot (199 rows, "42 fake futures wins... 1 clean winner is RELIANCE"). I reran `build_meta_labels.py` directly against the live `meridian_v3.db` into a scratch directory (not overwriting the tracked artifacts): **216 rows**, win rate all 25.9%, win rate clean (`is_futures==0`) **3.0% (5/165)**, avg honest PnL clean **−₹8.34**, sum **−₹1,376.52**. None of these numbers match any shipped artifact.
- **Why it matters:** Whoever reads the checked-in CSV, the analytical report, or the metadata README today is looking at a book state that no longer exists on disk anywhere in this repository. Any decision made from those files (including "the model is profitable" or "the model loses money") is not about the current desk.
- **What "fixed" would look like:** Regenerate the artifacts from the current DB before every review/train, and stamp the CSV/DB with the source DB's row counts or a content hash so staleness is detectable at a glance. (README_MeridianV3_MetaLabels.md is itself commendably candid about the futures-mark and belief-poisoning problems — it should be treated as the most trustworthy of the three documents, but it too is stale relative to the DB I inspected.)

### F9 — Severity: medium — Doc/config drift: which capital figure and which concurrency limits are binding

- **File:** README.md (top: "starts at ₹50,000"; bottom: "You can lose the whole ₹5,000"; bullet 3: "₹5,000-aware sizer"), `docs/03-capital-sizing.md`, `docs/06-data-flow.md`, `docs/07-safety.md`, `docs/10-phases.md` — all written for a ₹5,000 book (cash reserve ₹500, 1 INFY share leaves cash ₹3,512, concurrency "2 normal / 4 high") — vs. `config/default.yaml:account.starting_equity_inr=50000`, `SizingCfg.max_concurrent_normal=16/max_concurrent_high=20`.
- **What I verified:** Code and the live DB are unambiguous and internally consistent at ₹50,000 (`account_state` peak 57,392). The docs disagree with themselves inside the same README, and every capital-sizing doc uses the old ₹5,000 worked example verbatim, including a concurrency limit (2/4) that is off by 8× from the shipped config (16/20).
- **Why it matters:** A reader (or a future contributor) trusting docs/03/06/07/10 will materially misjudge position sizing, cash-reserve floors, and how many clips can be open at once.
- **What "fixed" would look like:** A single documented pass updating docs/03, 06, 07, 10 and the two stray README lines to ₹50,000 and the real concurrency numbers, or a template variable so this can't drift again.

### F10 — Severity: medium — No second line of defense for options-buy-only / no-standard-FX-lots at the broker layer

- **File:** `meridian_v3/execution/brokers/paper_broker.py:19-49` (`PaperBroker.place`), `meridian_v3/execution/oms.py:43-114` (`_send`).
- **What I verified:** Neither `PaperBroker.place()` nor `OrderManager._send()` inspects `req.market` for market-specific rules (buying-only, lot-size floors). Both currently work only because `decision/engine.py` and `capital/sizer.py` never *produce* a disallowed order today. There is no assertion at the execution boundary that would catch a future regression in the decision layer (e.g., a bug that lets `action=="sell"` through for `options_buy`).
- **Why it matters:** Docs/02, docs/03, docs/07 all present "options buying only" and "no standard FX lots" as safety rules, implying they're enforced where money moves. Today they're enforced only upstream, once, in a layer that already has (per F1-F3) at least two other bugs.
- **What "fixed" would look like:** A cheap `assert`/reject in `OrderManager._send` or `PaperBroker.place` keyed on `market` (reject `side=="sell"` for `options_buy`/`crypto_options`; reject `qty` above the configured lot ceiling for `forex_micro`).

### F11 — Severity: medium — Old-book ₹5,000→₹50,000 migration has a gap

- **File:** `meridian_v3/storage/db.py:_migrate` (SQL: `WHERE peak <= 5000.01 AND peak > 0`), `meridian_v3/storage/seed.py:202-220` (`lift_book_to_start`).
- **What I verified:** The SQL migration only lifts accounts whose `peak` is still at-or-below the original 5,000 ceiling. An account that had already compounded past 5,000 (e.g. `peak=5,200`) before this migration ran is skipped by that `WHERE` clause. The Python-side fallback in `seed.py:lift_book_to_start` only fires when `abs(equity-cash) < 1.0` (no open positions) and `not live_armed` — a partially-invested old-scale book with open clips satisfies neither path and is left permanently on the old ₹5,000 basis.
- **Why it matters:** A book in this specific gap state would silently run at 1% of the intended bankroll indefinitely, with every downstream rupee figure (Kelly sizing, cash reserve, drawdown %) computed against the wrong scale.
- **What "fixed" would look like:** Widen the SQL condition (e.g. compare `cash+equity` against the account's own fill history rather than a fixed peak threshold), or add an explicit one-time `schema_version`/"migrated" flag instead of inferring migration state from `peak`.

### F12 — Severity: medium — USDINR fallback is a silent, unflagged hardcoded constant

- **File:** `meridian_v3/data_providers/service.py:286-290` (`_usdinr`).
- **What I verified:** `_usdinr()` returns the live `price_cache` value for `USDINR` only if present and `> 50`; otherwise it silently returns `83.5` with no log line, no `quality="stale"` flag, and no propagation of "this mark used a fallback" onto the resulting commodity/FX `PriceCache` rows it feeds (`_to_inr`, `_scale_ohlc`, `_refresh_binance`). This fallback is used to convert every COMEX/NYMEX/ICE commodity mark and every non-INR FX pair into rupees.
- **Why it matters:** If USDINR ever fails to fetch (network hiccup, Yahoo throttling, or simply before the first successful refresh after a fresh seed), every commodity and cross-FX price on the book is silently off by however far 83.5 has drifted from the live rate, with nothing in the UI or logs to say so.
- **What "fixed" would look like:** Surface a `quality="fx_fallback"` marker on affected `PriceCache` rows and a visible banner/log line whenever the fallback is used, and consider failing the refresh for those symbols rather than marking them "live" with a stale FX cross baked in.

### F13 — Severity: low — `/desk/cycle` notice text is unconditionally wrong about live state

- **File:** `meridian_v3/ui/routes.py:248-264` (`desk_cycle`).
- **What I verified:** The success notice hardcodes the string `"Live stays disarmed."` regardless of `result["live_armed"]` or whether any clip actually cleared the live gate on that pass.
- **Why it matters:** This is the one screen meant to tell the operator what a manual cycle just did; if live actually is armed, the message is simply false.
- **What "fixed" would look like:** Interpolate from `result["live_armed"]`/`result.get("paper_clips")` instead of a fixed string.

### F14 — Severity: low — Silent exception swallowing on boot repair

- **File:** `meridian_v3/storage/db.py:88-102` (`_repair_book`).
- **What I verified:** `except Exception: session.rollback()` with no logging of `exc`.
- **Why it matters:** A repair failure on startup (e.g. a schema mismatch) produces zero diagnostic output; the operator has no way to know repair silently didn't run.
- **What "fixed" would look like:** Log the exception (the module already imports nothing from `meridian_v3.logging`, but the project has a `logging.py`) before rollback.

### F15 — Severity: low — Repair mutates the historical `Fill.note` text in place; the fill journal is not append-only

- **File:** `meridian_v3/storage/repair.py:169-196` (`_scale_fills`, `_rewrite_price`, `_rewrite_pnl`).
- **What I verified:** When `repair_shifted_clips` rescales a fill's price, it also does an in-place string-replace on that `Fill.note` (`fill.note = _rewrite_price(fill.note, old, fill.price)`), and separately rewrites the `"P&L ₹…"` substring of the paired exit fill's note (`_rewrite_pnl`). Both are literal text substring rewrites of the original `"PAPER FILL: BUY … near ₹380.06"` / `"PAPER EXIT: … P&L ₹39"` audit strings.
- **Why it matters:** The `Fill.note` column is the only free-text record of what the system believed at the moment of the trade (it's also what the UI's `_exit_reason` display and this audit's own evidence trail read from). Rewriting it after the fact — even to correct it — means the note no longer reflects what was actually written to the book in real time, and there is no separate audit-log table preserving the pre-repair text. A reviewer reading only `fills.note` today cannot tell a fill was ever wrong in the first place.
- **What "fixed" would look like:** Leave `Fill.note` immutable and either add a `repaired_note`/`correction_json` column, or record repairs as their own `desk_events` row referencing the fill id, so the original ticket and the correction are both preserved.

### F16 — Severity: low — No re-entry cooldown; the same symbol can open, close, and reopen many times a session, paying fees each time

- **File:** `meridian_v3/pipeline.py:245-250` (only blocks re-adding while a position is **currently open and same side**; nothing throttles opening a **new** clip on a symbol shortly after the previous one on it closed).
- **What I verified:** In the live DB, several symbols (`INFY.F` ×43, `BHARTIARTL`, `HCLTECH`, `BAJAJFINSV`, `BNBUSDT`, and others) show many separate closed positions rather than one held position, consistent with the desk re-deciding the same name on back-to-back ~60s cycles once a prior clip on it has closed. Each cycle pays brokerage + GST again. This compounds Finding F1 (same-price EOD losses): a name that never moves can still be opened and fee-charged repeatedly within one session.
- **Why it matters:** Even after F1/F2/F3 are fixed, a name with no real signal change can still bleed fees at a multiple of what a single-entry book would, because nothing prevents `run_cycle` from re-opening the same symbol every time it ranks near the top again.
- **What "fixed" would look like:** A minimum re-entry gap per symbol (e.g. `reentry_sec` — already computed as a training feature in `build_meta_labels.py` but not enforced anywhere in the live decision path) or a same-session "already traded this name N times" cap.

### Verified — no finding (checked because the brief specifically asked)

- **GOLD vs GOLD.X collision:** none found. `router/markets.py:market_for` and `universe/global_markets.py:is_global_commodity` correctly disambiguate by suffix — bare `GOLD` (asset_class `commodity`) routes to `equity_cash` via `_INDIA_COMMODITY_PROXIES`; `GOLD.X` routes to `global_commodities`. No shared cache key collision found in `_copy_cache`/`_to_inr`.
- **Indian STT/stamp fabricated on non-Indian tape:** not found. `charges/indian.py:_stt`/`_stamp` return `0.0` for `kind in {"crypto","fx","commodity"}`; only a broker brokerage line + GST-on-brokerage applies to those markets, which is defensible (an Indian discount broker's own commission does still apply to an INR-denominated crypto/FX/commodity paper clip).
- **Live can fire while disarmed or with no adapter:** not found. Traced end-to-end: `safety/guards.py` blocks `allow_live` unless `live_armed`; `decision/engine.py:192-197` additionally requires confidence ≥0.82 and confluence ≥62; `OMS._send` for the `live` venue routes through `PluginBroker`, which returns `ok=False` with a clear rejection message when `get_live_broker()` finds no registered adapter (`execution/brokers/plugin.py`); `OMS._send` only writes `Fill`/`Position`/touches account cash `if result.ok`. No path bypasses all three gates. Separately, `autopilot.tick()` hardcodes `run_cycle(session, live_armed=False)` (`autopilot.py:109`) — the unattended 60-second worker can never even attempt live, only a manual "Run cycle" click or `python -m meridian_v3 cycle` reads the true `live_armed` flag. This extra layer is good practice but is undocumented anywhere in ARCHITECTURE.md/docs/04.

## Training data

**Not usable as shipped.** Three problems compound:

1. The checked-in CSV/DB artifacts do not correspond to the live `meridian_v3.db` at all (Finding F8) — they reference fills that don't exist in any DB file in the folder.
2. Even a fresh, correctly-built dataset (which I generated, 216 rows) is dominated by the two DB-integrity bugs above: `INFY.F`/`NIFTY.F` contribute a fabricated ~100% win rate (43/43, 8/8) from a unit-mismatch bug, and the "clean" (non-futures) subset's 3.0% win rate (5/165, avg −₹8.34) is mostly fee-only non-events on a static daily mark rather than a measured negative edge.
3. Shorts are dropped by the round-trip reconstructor, and the reconstructor has a latent mis-pairing bug that would fabricate fake long trades the first time a short actually appears in the book (Finding F7) — untested, unguarded.
4. `p_success`, one of the twelve `CORE_FEATURE_COLS`, is not a learned signal — it's a fixed formula recomputed identically every time (Finding F4), so any model trained on this column is really training on confluence/freshness/cost restated, with extra circularity risk if that's not understood by whoever builds on top of it.
5. Sample size: even the fresh 216-row pull is 165 "clean" rows spanning a single day's demo session — nowhere near enough to support any win-rate or expectancy claim, and the authors' own `README_MeridianV3_MetaLabels.md` says as much for their (differently-sized, also-stale) snapshot.

`README_MeridianV3_MetaLabels.md` is the most self-aware document in the repo — it already independently documents the futures-mark contamination and the belief-poisoning effect, in numbers consistent with what I found. It should be read before anything else in `artifacts/`, but it too needs to be regenerated against the current DB before being trusted for a specific number.

## Architecture

**Boundaries that hold:**
- Proprietary math (`engine/`, `risk/`) does not leak into `api/` or templates — checked every `/api` route and `domain/reviews.py`/`domain/copy.py`; only scalars, plain text, and net Greeks cross the boundary.
- Review-copy discipline (`assert_review_copy`) is enforced structurally (raises on violation), not just by convention, and is unit-tested.
- Live-arm chain is genuinely defense-in-depth: arm flag, confidence/confluence thresholds, and adapter-presence are three independent gates, verified by code trace, not just by claim.
- Paper-never-pauses and the India-weekend-spares-crypto/FX/commodities rules both hold exactly as documented.

**Boundaries that leak or don't exist as documented:**
- The router's "equity home, visitors must beat it by a margin" competition is inert; real routing is suffix dispatch (Finding F6).
- V1 scoring (Finding F5) and the meta-label logistic's online-learning half (Finding F4) are advertised as live inputs but are dead code — the "V1 → V2 → V3" layered diagram in ARCHITECTURE.md is not what actually executes on the auto-decision path; V2's Greeks/risk engine likewise only feeds the manual `/api/review/{symbol}` page, not `pipeline.py`/`decision/engine.py` at all (no import of `meridian_v3.risk` anywhere under `pipeline.py`, `decision/`, `capital/`, `autopilot.py`).
- Walk-forward robustness gating (Finding F6 note in table) is implemented and tested but not wired.

**Dead modules confirmed by grep + zero-row DB check:** `scoring/composite.py` (unimported), `engine/walkforward.py` (unwired into `pipeline.py`), `engine/meta_label.py:OnlineLogit.update` (uncalled in production).

**One cycle, one place:** confirmed `pipeline.run_cycle` is the single implementation; both `autopilot.tick()` and `ui/routes.py:desk_cycle`/`cli.py:_cycle` call the same function (no duplicate/diverging cycle logic found). They differ only in the `live_armed` argument they pass (autopilot always `False`; the manual paths read the DB flag) — documented above as a feature, not a bug, but currently undocumented anywhere else in the repo.

**SQLite locking:** `storage/db.py` sets WAL + `busy_timeout=30000`; `autopilot._loop` and every UI mutation route acquire `desk_lock` (a `threading.RLock`) before touching the session. Did not attempt to force an actual deadlock under concurrent load — see "What I did not check."

## What I did not check

- Did not attempt to trigger or force a live fill by registering a fake `BrokerAdapter` — the code-trace proof in "Verified — no finding" above is a static trace, not a runtime exploit attempt.
- Did not force concurrent `Seed`-click + autopilot-tick contention to empirically test the `desk_lock`/WAL claim under load; read the locking code and consider it plausible, not proven.
- Did not fully audit `risk/` (Greeks/gamma/vega) or `scoring/composite.py`'s internal math for correctness — confirmed they're unreachable from the auto-decision cycle (scoring) or only reachable from the manual review API (risk), and treated deep validation of their formulas as out of scope given they don't touch money in this build.
- Did not exhaustively classify every one of the 190 closed positions' exit reasons by hand — sampled and pattern-matched via SQL/ratio checks rather than reading all 190 fill notes individually; the "tape flipped" cause in the same-price-clips table above is an acknowledged gap.
- Did not test the OCR/PDF/image ingestion path (`ingestion/ocr.py`, `ingestion/pdf.py`) end-to-end with a real scanned statement; only read the code and the CSV fixture test.
